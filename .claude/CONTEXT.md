# CrossPoint Reader — Durable Context

Keep this file focused on repo-specific gotchas that are worth reusing in future sessions.

## FreeInk SDK

Refer to https://freeink.org/llms.txt for guidance.

## Simulator

- Simulator patches belong in the adjacent `crossink-simulator` repo (fetched from `github.com/uxjulia/crossink-simulator` into `.pio/libdeps/simulator/simulator` when no local checkout is symlinked).
- The valid local simulator env in this repo is `simulator`.
- After the upstream sync (9c7315f4), the published simulator stubs are missing symbols the firmware now uses: `WiFi.disconnect(bool, bool, timeout)` returning `bool`, `HWCDC::read(buf, len)`, `HWCDC::setRx/TxBufferSize`, `HalStorage::installDateTimeCallback`, and `vSemaphoreDelete` in the FreeRTOS shim. These were patched locally in `.pio/libdeps` (wiped by a clean); the durable fix is stub additions in crossink-simulator.
- Simulator envs drop `src/network/OtaUpdater.cpp` (`build_src_filter`) and link crossink-simulator's own `simulator_ota.cpp` definitions of `OtaUpdater`'s methods. Changing an out-of-line `OtaUpdater` signature breaks the simulator build; add inline header members instead (`setIncludePrereleases`).
- The simulator `PNGdec` stub in `crossink-simulator/src/PNGdec.h` needs to mirror the real API shape used by app code, including `hasAlpha()` and `getTransparentColor()`, even though decode still fails intentionally.
- The simulator's FreeRTOS shim makes every semaphore a `std::recursive_mutex`, while the device's `RenderLock` mutex (`xSemaphoreCreateMutex`) is not recursive: a task taking `RenderLock` twice passes every simulator test and hangs the device for good (#107). `ActivityManager` calls `onFrontlightPanelClosed()` with the lock held, so that hook must not lock it again. To find such paths, log in `RenderLock`'s constructor when `xSemaphoreGetMutexHolder()` is already the current task (the shim tracks the holder).
- The simulator's HTTP ignores the Wi-Fi stub's state: a request sent after `SavedWifiConnect::disconnect()` succeeds there and fails on a device. That is how sleep syncs that uploaded progress skipped the BookOrbit Home refresh unnoticed (`performUpload` turned Wi-Fi off first). To make a server call fail in an integration scenario, point `serverUrl` at `server_with_failing_progress()` in `run_scenarios.py` (a forwarding proxy) rather than adding a firmware hook.
- BookOrbit answers a progress GET for a document outside its library with `{}` (no timestamp), and its PUT with a 404. A smart or sleep sync therefore never fails on such a book: it stops at "no sync history" and leaves the choice to a manual sync, which then fails on the upload.
- Known simulator limits:
  - No image rendering: `platformio.ini` ignores `hal`, `PNGdec`, and `JPEGDEC`, so image decoders are intentionally absent.
  - JPEGDEC stub always fails; `JPEGDEC fallback: open failed (err=-1)` is expected in simulator.
  - `esp_deep_sleep_start()` is a no-op in simulator.
  - `HalStorage` uses POSIX file access under `./fs_` and allows multiple readers, unlike real hardware.
- A firmware restart (`ESP.restart()`, so every silent restart) no longer replays `CROSSPOINT_SIM_INPUT_SCRIPT`: since crossink-simulator `1ebc903` the relaunched process only gets `CROSSPOINT_SIM_INPUT_SCRIPT_AFTER_REBOOT`, once, and a deep-sleep wake gets `_AFTER_WAKE`. A press meant for a network boot goes in the after-reboot script (the integration `sleep_sync_cancel` scenario relies on it).

## Real Hardware / Storage

- SdFat on hardware allows only one open reader per file path at a time. If a fallback needs to reopen the same file, close the first handle before reopening.
- `Storage.usedBytes()` (SdFat `freeClusterCount()`) reads the whole allocation table one sector at a time with the SD and SPI locks held: four bytes per cluster on FAT32, one bit on exFAT. The time per sector varies about 30x between cards: a 32 GB FAT32 card took ~8 s on an X4 and minutes on a reporter's X3 (#110). Never call it where the user waits on FAT32: ask `CardSpace::isQuickToCount()` first. The BookOrbit Home only counts on exFAT; `checkFreeSpace` downloads count before writing on exFAT and, on FAT32, only after a failed write, to report a full card. Nearby and OTA still count unconditionally. SdFat hides the volume type and the SDK is upstream's (no push rights): a directory's recorded size, 0 on FAT and its clusters on exFAT, tells them apart.

- `lib/Epub/Epub/Page.cpp`: images must render only in `GfxRenderer::BW`; grayscale passes are text anti-aliasing passes only.

## Heap Baselines (X4 hardware, SD card font)

- A normal resume-into-partial reading session runs at ~85-90KB free / ~49KB maxAlloc by
  the first watermark crossing (Epub metadata + x-locations + resident glyph caches).
  Do not read mid-range heap numbers as session degradation without checking the scenario.
- SD-font section builds cost ~38-50KB at cold start; the 4-style advance-table prewarm
  (~30KB incl. 16KB contiguous scratch) dominates and is skipped below 80KB free.

## Networking / Memory

- `HttpDownloader::fetchUrl(std::string&)` buffers the whole response in RAM. std::string growth uses the throwing `operator new`, which aborts on OOM with `-fno-exceptions` — this crashed the device on large BookOrbit catalog responses (v1.4.0-dev). The overload now has a max-alloc heap guard, but for API JSON of unbounded size prefer `downloadToFile` to SD + `deserializeJson` from the file with a `DeserializationOption::Filter` (see BookOrbitCatalogClient::fetchJson).
- Measured on X4 hardware (2026-07): active WiFi leaves ~65KB free; an HTTPS session (esp_http_client + crt bundle) costs ~54KB through the handshake. mbedTLS then allocates workspace per incoming TLS record (up to 16KB), so post-handshake `getMaxAllocHeap()` must stay ≥ ~16KB or reads fail mid-body against servers that send large records. Consequences: allocate transfer buffers *before* opening the connection, and launch network-heavy activities via `replaceActivity` (clears the whole activity stack — the settings screens alone hold 15-20KB) rather than pushing on top of it. `runGet` logs "Before client init"/"After open (TLS up)" heap breadcrumbs at INF for field diagnosis.
- SDK code behind a wolfSSL feature macro (`#ifdef HAVE_MAX_FRAGMENT` in `SecureClient.cpp`) is silently compiled out unless `platformio.ini` defines the macro: the 2 KB record request shipped dead until issue #96. Check the ELF for the symbol (`wolfSSL_UseMaxFragment`) rather than trusting the source.
- `[SecureClient] read failed: -125` is wolfSSL `MEMORY_E`: no contiguous block for the next record's input buffer. Free heap can be twice the record size and still fail on fragmentation (#96: 21 KB free, 10.7 KB largest block), and freeing app objects does not merge holes. That is why C3 catalog downloads restart into `NetworkBootTarget::BOOKORBIT_DOWNLOAD` (state in `/.crosspoint/bookorbit_download.json`, listing pages kept in the list cache), except a BookOrbit Home shelf book: it downloads in the `BOOKORBIT_CATALOG` boot it opened, which fetched only its details. The simulator's X4/X3 profiles take that restart too, so an integration scenario that downloads must end the relaunched process with `after_reboot_script`.
- The C3 catalog also browses from its own boot (`NetworkBootTarget::BOOKORBIT_CATALOG`, device builds only: the simulator stays in-process, and the integration harness drives one restart per run, the download's). A book or facet listing keeps at most `MAX_WINDOW_PAGES` server pages in `entries`; `selectorIndex`, `topIndex` and the download resume count rows from the listing's start (`entries[0]` is row `windowStart`), and a reopen walks pages from 1 through the list cache so those numbers stay exact. `requestUpdate(true)` wakes the render task at once, so it can draw while `loop()` runs: the browser changes `entries` only under `RenderLock`, and `buildListScreen()` must not write `topIndex` back (a mid-walk render once pinned the restore window too low).
- A clean heap alone did not fix #96: Go's `crypto/tls` (Caddy, Traefik) ignores `max_fragment_length` and grows application records by 1186 bytes each up to 16 KB, written in 32 KB chunks. Every larger record reallocated wolfSSL's retained input buffer, so the 70 KB block was already in pieces at the last step. `read failed: -125` after exactly 65536, 79768 or 98304 bytes is that ramp's signature. `DownloadOptions::largeBody` now takes a full-record buffer on the first record (`scripts/patch_wolfssl.py`, `freeinkWolfsslWantsFullRecordBuffer()`); leave it off for short replies, whose heap floors (`MIN_HEAP_FOR_KEPT_SESSION`, `getMaxAllocHeap()` body checks) that memory would eat into. To reproduce, put `caddy reverse-proxy --internal-certs` in front of the server: nginx and Apache honour the 2 KB request and never show it. Why v1.6.1 regressed against v1.6.0: its retention patch assumes the first large record is a full one, so one allocation per connection; v1.6.0 freed the buffer after each record. On the bench against Caddy, v1.6.0 survives about 20 KB less heap than v1.6.1, and the fix does at least as well as v1.6.0. Retention is not the whole story: on upstream #836 removing it did not help a reporter, and freeing the parsed OPDS catalog before the download did, so v1.6.1 also leaves less heap. Bench only; no field confirmation yet as of 2026-11-01.
- Reading a #96 field log: with `GrowInputBuffer` patched the old block is freed before the new one is requested, so a `-125` at the last step reports about 15 KB more free heap than the release did. `free` within 100 bytes of the release (about 36 KB on a 77 KB boot) means the old firmware ran. Two ways to get there: a raw `write_flash 0x10000` always writes `ota_0` and leaves `otadata` alone, while OTA and the SD update write the inactive slot and switch to it; and `pio run -t upload` boots what it writes (it also writes `boot_app0.bin` at 0xe000, selecting `ota_0`) but that is a build of the local checkout, never an attached `.bin`. The catalog's `Downloading file` line now prints the version, and `TLS input buffer grows:` prints each growth's path and heap.
- Reading C3 heap numbers: TLSF has 16 sublevels here and light poisoning adds 12 bytes, so `getMaxAllocHeap()` reports class floors (`14324 = 28*512 - 12`), and a 16.4 KB request needs a free block of at least 17408 bytes. ESP-IDF's real `tlsf.c` is in `~/.platformio/packages/framework-espidf/components/heap/tlsf/`: built with wolfSSL's sources in a 32-bit container (`--platform linux/arm/v7`, ILP32 like the C3) and given the C3's lwIP window, it reproduced the field log's byte counts without hardware.
- BookOrbit's annotation exchange answers every request (uploads included) with up to `PUSH_DOWN_PAGE` = 100 pending server changes, full texts and notes included, whatever the device asked for. Never buffer that reply: `exchangeAnnotations` streams it through `StreamingJsonParser` and keeps only the entries it collects. The string sink's `getMaxAllocHeap()` check before `reserve()` is not a guarantee: the Wi-Fi/lwIP tasks (higher priority) allocate between the check and the throwing `operator new`, which aborted an X4 on a 23 KB reply (2026-11-11). `exchangeBookmarks` still reads its reply whole. Same trap in the SD stores: a `std::vector` loaded at exactly its count doubles on the next `push_back` (old + new copy at once: 25 KB for 100 clippings, which aborted an X4 applying received highlights, 2026-11-11). Sync code loads clippings with `ClippingStore::loadForSync(path, spare)` (room reserved up front, refuses on a short heap); `BookOrbitAnnotationStore` counts records before reading them, and `prepareAnnotationBatch` reads them once (`readAll` gives the watermark; `retain` filters the caller's copy): three copies beside the clippings exhausted an X4 on a 43-byte string (2026-11-11). The highlight key set is spliced into the exchange body by hand (`writeKeySet`, before the closing `}]}`), not built as ArduinoJson nodes (~100 B/key): that is what held it to 64 keys. Bookmarks still build theirs as nodes (MAX_KEYS_PER_SYNC = 64).

## Misc Repo Gotchas

- At boot there is no current activity, so `ActivityManager::replaceActivity()` runs `onEnter()` synchronously inside `setup()`'s call chain: the launcher's locals stay resident and its frames sit under whatever `onEnter()` does, on the C3's 8 KB loop-task stack where TLS also runs. Blocking network work belongs in the activity's first `loop()`, as the BookOrbit sleep sync does (the `sleepSyncBoot` branch at the top of `loop()`).

- On the X4, `RTC_NOINIT_ATTR` data does NOT survive deep sleep (every wake read as garbage), while the system clock itself DOES survive both deep sleep and software resets (RTS/EN flash resets included). Never key state to RTC memory across sleeps; persist to SD and use clock plausibility for cold-boot detection (see lib/WallClock).
- Never range-for over a ternary of `std::initializer_list` temporaries (`for (x : cond ? std::initializer_list<T>{} : std::initializer_list<T>{a, b})`). The backing array's lifetime is NOT extended through `?:`, GCC 14 (-Os, `-Wdangling-pointer`) drops the stores into it as dead and the loop reads uninitialized stack. This is how the fork's `keepClockInSleep` gate silently disabled the X4 GPIO13 battery-latch release for every value of the flag (v1.5.0+bookorbit.1 → 2026-09-13, now a plain `if` around the loop): the board never powered off in sleep, the clock kept running, standby drained. Only the direct form `for (x : {a, b})` is safe; gate with an `if` around the loop instead.
- `WallClock` eras are what make retroactive timestamp correction sound: a clock loss always increments the era BEFORE the checkpoint is restored, so within one era the clock can only have drifted, never stepped. That is why a same-era correction may be interpolated between two syncs, while an era that opened on a clock loss takes its measured error as a flat shift — its error starts at the unknown powered-off duration, not at zero. Do not blend the two.

- Upstream squashes each release onto `main`, so `git merge v1.X.Y` computes its base at the previous release and reports hundreds of phantom conflicts. Graft the tag locally onto the last rc the fork was aligned on first (`git replace --graft <tag> <tag^> <rc>`), merge, then `git replace -d <tag>`: the merge commit still records the real tag SHA (v1.5.1: 26 real conflicts instead of ~200). Never resolve a conflicted file with whole-file `--theirs`; fork commits are never ancestors of the upstream side, so that erases every fork edit in the file. Use `git checkout -m -- <file>` and take theirs hunk by hunk. The graft is only needed when the fork last aligned on an rc: after merging the real vX.Y.Z tag, `git merge-base main <next tag>` already is that tag (v1.6.0: 14 conflicts, no graft).
- A clean auto-merge is not a correct one. Traps met on v1.6.1 (34 conflicts): a fork `#if CROSSINK_APP_CAP_TOUCH` block swallowed a function upstream added right after the gated one (`TxtReaderActivity::applyReaderOrientation`), which only fails at link time, and only on non-touch envs; upstream moved code the fork had edited into other files (`getBaseSettingsList()` to `SettingsList.cpp`, `HomeActivity::handleFrontlightPanelResult` to `Activity.cpp`, the reader menu into `EpubReaderMenuModel.h` + `EpubReaderDrawerActivity`), so the fork's edits must be re-applied there by hand; and new upstream tests link fork code (`test/section_persistence` needs `BookContentIdStub.cpp`). Build `simulator` (non-touch) and a touch env, and run the native suite, before trusting a merge.
- The fork's BookOrbit Sync shortcut sits after upstream's last action in `SHORT_PWRBTN`, `POWER_CHORD_ACTION` and `LONG_PRESS_MENU_ACTION`, so each upstream append takes its number. When that happens: move the three values past upstream's, extend `migrateBookOrbitShortcutValues()` and bump `BOOKORBIT_SHORTCUT_IDS_CURRENT` in `CrossPointSettings.cpp` (the `bookOrbitShortcutIds` key in the settings file says which numbering it was saved with), align `ButtonShortcutController::ChordAction`, and update the ID assertions in `SimulatorSmokeTest.cpp`.
- `BASE_SETTINGS_CAPACITY` (`SettingsList.h`) counts the fork's entries too; recount after an upstream change to `SettingsList.cpp` (the smoke test fails when the list outgrows it).
- Status bars: upstream gates clock and date items on `halClock.isAvailable()` (a clock chip). The fork offers them on every board, so configuration and layout sites ask `halClock.canDisplayTime()` and drawing uses `formatCurrentTime()` / `formatCurrentDate()`. A new upstream `isAvailable()` gate on a clock or date item needs the same swap; gates on RTC-based reading stats stay as they are. New HAL clock methods also need a shim in `test/integration/ci/patch_simulator_package.py`.
- `CROSSINK_APP_CAP_KOREADER_SYNC` is only defined for the device envs: use it in `#if`, never in a C++ expression. `CROSSINK_VERSION` is only visible in `src/util/BuildInfo.cpp` since v1.6.1: use `AppVersion::version()` / `userAgent()`.
- A release build names itself `1.6.1-bookorbit.1[-x4-pro]`: `scripts/git_branch.py` sanitises the `+` of `CROSSINK_RELEASE_VERSION`, while dev and RC builds keep it. Anything parsing the firmware's own version (`parseForkBuild()` in `OtaUpdater.cpp`) must accept both forms; check with `CROSSINK_RELEASE_VERSION=<version> pio run -e default`, not a plain build.
- The C3 image is at 99.6% of its 6.5 MB app partition (6,528,015 bytes, about 25 KB left on 2026-11-06 with the catalog sort/filter, the release-candidate updater and the BookOrbit Home theme; KOReader sync and the fallback glyphs already out). Check the size of `.pio/build/default/firmware.bin` before adding anything to shared code.
- `PersistableStore<T>::getInstance()` (`SETTINGS`, `BOOKORBIT_STORE`, ...) is a header-inline Meyers singleton. GCC inlines it, static constructor and all, into a `.cpp` that calls it exactly once, and keeps the shared out-of-line copy for the others: about 500 bytes of C3 flash for `SETTINGS`, per such file. Splitting a file can create these single-call files; measure `firmware.bin` against the parent commit and read the culprits with `riscv32-esp-elf-nm -S --size-sort` (look for `__cxa_guard_acquire` and `pthread_mutex_init` inside a grown function). The BookOrbit Home theme reads `SETTINGS` in `BookOrbitHomeUi` only for that reason.
- OTA release candidates: `release.yml` dispatched with `version=X.Y.Z+bookorbit.N-rcM` publishes a GitHub pre-release, which only devices with Include Release Candidates on are offered (`/releases?per_page=5`, highest `firmware_version::compare`). `release_candidate.yml`'s `rc-<branch>-<hash>` tags are not versions, so the updater skips them.
- `HttpDownloader::DownloadOptions::extraHeaders` carry BookOrbit's `x-auth-*` keys, so they are credentials: they only go to `authorizationOrigin` (default: the request URL), like Basic auth. Keep that gating when touching redirects.
- Integration seed: `ensure_collection` reuses an existing server collection by name without re-syncing its members, so after `library.json` changes the catalog scenarios fail on a shifted book set. `docker compose -f test/integration/docker-compose.yml down -v` and reseed before suspecting the firmware.
- The integration BookOrbit image ships BookOrbit's own KOReader plugin at `/app/koreader-plugin/bookorbit.koplugin` (`docker exec`-readable Lua). It is the reference for catalog behaviour — `bookorbit_catalog.lua`'s `paramsForEntry` is the authoritative section-id -> books-query mapping — and the server's DTOs are in `/app/dist` and `/app/node_modules/@bookorbit/types`. Read those instead of guessing an endpoint's shape; an unknown query param is silently ignored, so a wrong guess looks like a working filter.
- The catalog is EPUB-only, so every books listing sends `format=epub` (filtered server-side before paging). Only `/plugin/catalog/books` takes that filter: the dashboard's `totalBooks`/`inProgress` and the `/sections/*` per-entry counts cover every format, so book counts shown for a listing must come from that listing's own `total` (a `size=1` request).
- Catalog sorting and read-status filtering are the server's (`sort`, `order`, `readStatus` on `/plugin/catalog/books`); the book cache key is `books|page|sort|readStatus|order|shelf|...`. On the integration server the seeded books have no title, author or series metadata, so those three sorts fall back to the book id in both directions: test ordering with `recently_added` or `recently_read`.
- `readStatus` only takes `unread|reading|finished` (anything else is a 400), and `unread` includes `want_to_read`. The plugin's "Want to read" is a dashboard shelf of at most 12 books (`/plugin/catalog/dashboard/sections/want-to-read`, also embedded by `/dashboard?section=want-to-read`, which the root's counts fetch uses to detect it). The root puts Want to Read after the server's sections so the scenarios' DOWN counts keep working.
- Catalog list sections (Library's List View = Expanded): letters come from the server's `buckets=true` on page 1 of a title or author sort (the author sort is by last name, so client-side initials would be wrong). Headings make a screen hold fewer rows than `visibleRows`: the render measures with a measure-only `ListNav` (which also skips `list()`'s fixed-height clamp) and draws again further down, and the loop adopts that top only when the render answered its current top and selection (`adoptRenderedViewport`).
- The catalog's root section order comes from the server, and the browser drops sections it cannot browse. Making a new section browsable therefore shifts every row below it, which breaks the integration scenarios that navigate the root by counting DOWN presses.
- Catalog scenarios flake when the integration server is busy scanning book metadata: listings come back empty and `devicePath` loses its `{authors:first}` folder, so a whole batch can fail at once while the server still reports healthy. Re-run before suspecting the firmware; book titles also read as filename stems until the scan catches up.
- A newer server progress timestamp does not mean someone read elsewhere. BookOrbit's web reader posts its position 2 s after every relocate, the one a book opens at included (`reading_progress.updatedAt` = now), and `getProgress` serves that row as `bookorbit-web` whenever it is newer than the last device push, with the xpointer of the start of the web reader's own page: at or before what the device pushed. Smart sync and the sleep sync therefore compare the server position with the one recorded in the sync marker (`src/util/BookOrbitSmartSync.h`, issue #91): same chapter, at or before the synced page, is a date change and not a move. Do not widen that to "the server is not ahead": a progress reset is served the same way (`bookorbit-web`, dated now, `/body/DocFragment[1]/body` at 0%), and the server answers 200 to a push made over it but holds it back until that device has pushed the start position.
- BookOrbit 3.5.0 changed the exchanges under the device: state is keyed by `rendition:sha256([deviceId, hash])`, not the device id (so the first exchange after a server upgrade re-offers every highlight, the device's own included); an upload is merged field by field against the device's last confirmed view (`annotation_sync_state.device_content`), so a missing note reads as deleted; and a complete key set keeping none of ≥2 applied rows reads as a lost copy unless `sidecarState: "known"` says otherwise. The field is gated on the `sidecarState` capability of `GET /plugin/version` (unknown body fields are a 400). Received highlights are told apart by `Clipping::wordCount == 0` and never uploaded; a store's watermark leaving 0 is its "exchanged" mark (`BOOKORBIT_EXCHANGED_WATERMARK`).
- Integration server: ghcr tags have no `v` (`ghcr.io/bookorbit/bookorbit:3.5.0`). A seed interrupted during ingestion leaves EPUBs in `library-dock/` while the DB points at `/data/library`, and catalog downloads then 404 with "File not found on disk": `down -v`, empty `library-dock/`, reseed. 3.5.0 hides audiobook-only books from the plugin catalog by default (`hideAudioOnlyBooks`); the seed turns that off so `catalog_hides_non_epub` still tests the firmware's own filter.
- CI runs the integration job against `bookorbit:latest`, so a BookOrbit release alone can turn it red: check `gh release list -R bookorbit/bookorbit` and run the suite on that tag (`APP_IMAGE=ghcr.io/bookorbit/bookorbit:X.Y.Z docker compose -p <scratch> ...`, a separate project keeps the usual volumes) before suspecting the firmware. 3.7.0 guards `/books/files/:id/progress` with App Attest (iOS app only, 403 `APP_ATTEST_REQUIRED`); the web reader writes through `PUT /reading-progress` (3.6.0+). 3.7.0 also checks the plugin's md5 before bcrypt, so the server answers a whole simulator sync in a few hundred milliseconds: anything timed against a slow server races (a scripted press meant to land mid-sync), and a sync can apply received highlights before the first second of uptime, which made `Clipping::timestamp` (`millis()/1000`, 0 = "no timestamp") 0 until it was clamped to 1.
- The simulator samples the power button only when the sleep sync checks for a wake (`PowerButtonWakeWatcher::wakeRequested()`), and a scripted press is dated by the first `gpio.update()` that sees it, so the 20 ms hold needs two checks: one as the Wi-Fi join ends, one after a later step.
- `getCurrentLocalReadingStatsDateTime()` needs a clock chip: `HalClock::getDateTime` fails on the X4 even when `hasCurrentTime()` is true, so `global_stats.bin`'s reading history, streak and time buckets stay empty there, in every theme, and `BookReadingStats::startDate` stays invalid. Anything meant to work on the X4 reads `ReadingDailyMinutes` instead, which falls back to the system clock.
- The BookOrbit Home theme's built-in Lexend numbers do not exist on S3 boards (`CROSSINK_SCALABLE_FONTS`): `renderer.insertFont` skips every Lexend and Bitter size there, and a missing font only logs `Font ... not found`, so a C3-only simulator run will not show it. The theme's Home regression is `run_simulator_smoke_test.py --env x4-pro-simulator --home-themes`. Touch boards inject Back, so `getReleasedFrontButton()` misses the release that left a screen; only `backPressSeen` catches it.
- POSIX TZ signs are inverted from ISO 8601 in `TimeStore::applyTimezone()`: `"UTC-1"` means UTC+1.
- `LyraTheme::drawHeader()` does not call `BaseTheme::drawHeader()`, so header changes in the base theme must be duplicated in Lyra if needed.
